# Private performance consultation

`performance-consultation.mjs` composes the existing `createNativePodClient` encryption, native identity checks, signed readback and compare-and-swap updates. For Hallowmarch, its stable encrypted named graph has one owner-key-authenticated encrypted native checkpoint resource. The initial signed binding is published once; subsequent compare-and-swap updates replace that resource without publishing a fresh context descriptor or creating history pages. Neither observation bodies nor consent records go through a Hallowmarch game endpoint, database, public graph, public owner-agent grant, or local-storage record primary. Browser key custody and recovery reuse the existing native client.

Construct `createOwnerPerformanceConsultation({ binding, credential, relayUrl, sessionId, checkpoint: 'hallowmarch-performance-consultation/v1' })` from the current verified native owner connection. Use a random session identifier distinct from all bearer credentials. `connect()` and `read()` are read-only and never create an encryption key or consent. A missing existing key requires the ordinary native profile recovery flow; this module cannot replace it.

The separate `createFoxxiConsultant` setup verifies the current owner's session delegate before discovering or signing a coaching request. A fresh registry-only bootstrap may need its existing delegate's signing credential. Setup uses only the explicitly advertised native `repair_only: true` mode, checks exact owner/pod/agent and current write eligibility, and requires complete signed-chain readback. It never changes scope or registry authority. Already verified credentials require no setup write. Revoked, narrowed, foreign or otherwise invalid authority fails closed. Lost acknowledgements allow readback only from that consultant. Neither signing setup nor service discovery sends observations or grants consultation consent. Generic private journal reads and key recovery remain independent of signing authority.

The journal represents exactly `binding.subjectDid`. The relay client verifies that DID against its authenticated own pod. It does not substitute the OAuth signing delegate for the owner, accept a performer selector, or let a player write an agent's personal performance record. An agent uses its own authenticated connection and pod. `performerKind` classifies the self-attributed observation; the field never grants authority.

## Consent and delivery

Every consent scope includes all of the following: owner, application, current session, selected task, purpose, exact HTTPS recipient, and an expiry of at most fifteen minutes. The two purposes are:

- `retain-observations`, whose recipient must be the authenticated owner's pod.
- `request-consultation`, whose recipient must be the concrete discovered Foxxi action target.

Call `grantConsent({ accepted: true, purpose, recipient, taskId, lifetimeMs })` only for an explicit performer choice. A native OAuth grant, public gameplay relationship, resource consultation, or prior session permission is insufficient. `authorize({ purpose, recipient, taskId })` returns a consent token. After signing the exact previewed request, the service adapter must call `assertAuthorized(token)` immediately before transport. This rereads the current encrypted native index and rejects expiry, withdrawal, changed consent, wrong task, different subject/session and uncertain publication.

`revokeConsent({ purpose, recipient, taskId })` blocks this open connection immediately, including a queued capture awaiting key registration. It then confirms any outstanding native operation before writing the withdrawal with the current native head. A failed withdrawal stays locally blocked. Other connections observe a withdrawal after its native publication is confirmed; pending publication is not described as cross-device revocation. Starting a new consultation session never restores another session's permission.

Native initial named-graph creation has no atomic compare-with-absence primitive. The underlying client preflights absence and refuses forked readback. Uncertain writes block new writes and delivery until explicit `retry()` confirms the original operation. If the initial checkpoint binding is uncertain, Retry may reconcile only the already-frozen original binding plan; an ordinary read, authorization check, or withdrawal never republishes it automatically. The complete native head, including its checkpoint revision and record digest, is passed back as the next compare-and-swap expectation. Its stable binding CID alone is not a record revision. The journal never silently replaces its discovery graph or overwrites an unread competing head. On a native conflict, reopen the current owner record before making a new explicit choice.

## Bounded Hallowmarch history and continued use

Hallowmarch uses `checkpoint: 'hallowmarch-performance-consultation/v1'` explicitly in both the player UI and the agent's own-session adapter. The default Hallowmarch application ID also selects this mode, so a host cannot accidentally keep adding immutable history by omitting the option. A different explicit application ID retains the generic journal's existing immutable-history behavior.

The checkpoint keeps at most one hour of detail, at most 32 observations, 32 consultations and 32 evaluations, and at most 192 KiB of the complete private record. A busy hour or large responses can reach the count or byte limit sooner. The latest plan and the current append's necessary baseline/comparison bundle are preserved while valid; older detail is removed with dependent records, so an evaluation never points to a missing baseline. Responses that remain are exact and each is bounded to 32 KiB. This is a bounded recent working set, not a complete event archive or lifetime learning history.

Small cumulative `coverage.counts` track how many observations, consultations and evaluations were recorded. `coverage.pruned` states how many details are no longer present. These are observed record counts, with a saturation flag at the safe-integer boundary; they do not imply success, learning or mastery. Reads apply the one-hour window without writing. The next authorized mutation persists the compacted record. Expired short-lived purpose choices are also removed once outside the window. Native gameplay-agent grants, permanent delegations and security tombstones are separate resources and are never compacted here.

The limits do not freeze future use. Hundreds of subsequent mutations continue to replace the same journal resource without `client.create()` calls, archive pages or a growing descriptor chain. An uncertain native operation remains fenced even when its draft is older than the detail window. Nothing prunes or silently abandons its operation identity, and no capture or delivery can pass the fence. Explicit readback of that exact original operation must resolve it before later mutations proceed; after confirmation its old detail may age out while its cumulative count remains.

Existing generic v1 records are verified and read without migration writes. On the first bounded update, current known records become the bounded checkpoint and any old `archiveHead` pointer remains unchanged. `coverage.legacyHistoryUnknown` states that the cumulative counts do not include the old archived lifetime history. The journal never appends another archive page, automatically walks that chain, or resurrects old observations/plans as current evidence. `readArchive(reference)` still allows an explicit read of a pinned old immutable page and rejects changed references, wrong owners and cycles. Existing archived resources are not deleted by this module.

Generic journals under another application ID keep the prior sixteen-record/190-KiB archive rotation and 32-record/350-KiB safety bounds. Their explicit `readArchive` path and pending-operation reconciliation remain covered for backward compatibility; Hallowmarch does not use that storage mode.

## Honest task evidence

`appendObservation({ task, performerKind, evidence })` requires current task-scoped retention consent. Task fields are `id`, `desiredResult`, `observedResult`, `workContext` and optional bounded `constraints`. Desired/current result text is a performer report. Evidence entries are `{ kind: 'owner-browser-observation', performerDid, at, metrics }`, where the DID must equal the authenticated owner and measurements must be bounded finite nonnegative numbers. These are observations of the actual open game, not signed authoritative event-log proofs. Do not supply made-up measurements, achievements, other players' state, inventory, chat, credentials or hidden state. Changing a goal or work context requires a new task identity and consent.

`appendConsultation({ observationId, service: { action, target }, response })` retains the actual bounded service response in this owner pod. It requires retention consent, references an existing self-attributed observation, and labels the response `service-response-unvalidated-effect`. The Foxxi adapter separately enforces network consent and its signed subject-proof contract. No learner registration or remote `private_evidence` is needed to retain the returned unretained plan here.

Record a later real observation of the same task, then call `appendEvaluation({ consultationId, observationId, playerReport })`. This retains the performer report and actual before/after differences for matching measured values. It cannot create a success score, infer causation, assert learning or mastery, publish xAPI statements, enroll a learner or issue a credential. All records retain `competencyStatus: 'not-assessed'`. Delayed or unseen transfer testing requires additional authentic observations and evaluation; receiving a plan does not establish an effect.

`read()` returns cloned `{ schema, ownerDid, applicationId, consents, observations, consultations, evaluations, archiveHead, coverage }` snapshots in bounded mode; generic records can omit `coverage`. Existing v1 records without `archiveHead` remain readable. Append methods return `{ saved, reference, observation|consultation|evaluation }` only after verified native readback. Checkpoint references distinguish the stable signed `cid`/`bindingCid` from the changing `nativeRevision` and `recordCid`, and explicitly label `proofKind: owner-key-authenticated-checkpoint`; they are not fresh signed immutable observation descriptors. `status()` reports key presence, connection/pending state, archive head and current working-set counts. `close()` clears the open private index and rejects late asynchronous results.
